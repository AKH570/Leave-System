# cPanel deployment: `app.abirhkhandokar.com`

This guide is specific to this repository. The Django settings module is
`LeaveManagementSystem.settings`, the Passenger startup file is
`passenger_wsgi.py`, and the WSGI entry point is `application`.

Replace `CPANEL_USERNAME` below with the username shown in cPanel. Replace
`app` only if the final subdomain has a different name.

## 1. Hosting prerequisites and blockers

- Local runtime: Python 3.12.6 and Django 6.0.4.
- Required cPanel runtime: Python 3.12 or newer. Django 6.0 does not support
  Python 3.11. If Setup Python App does not offer 3.12+, ask the host to enable
  it before uploading; do not silently choose an older interpreter.
- Production packages are pinned in `requirements.txt`.
- Local database: SQLite (`db.sqlite3`). MySQL/MariaDB is recommended for
  concurrent production use. The settings retain SQLite for development and
  select MySQL when `DB_ENGINE=mysql`.
- The host must provide Setup Python App (CloudLinux Python Selector),
  Passenger, MySQL/MariaDB, Terminal or SSH, and a valid AutoSSL certificate.
- Migrations must be uploaded. Never add `migrations/` to `.gitignore`.
- Do not upload the local `env/`, `.env`, `db.sqlite3`, `.git/`, `media/`, or
  `staticfiles/` as application code. Transfer data/media separately and
  deliberately.

The exact Python versions and environment-variable UI are controlled by the
hosting provider and cannot be discovered from this local repository. Confirm
them in **cPanel > Software > Setup Python App** before deployment.

## 2. Recommended directories and subdomain

```text
/home/CPANEL_USERNAME/
|-- leave_management/          # private Django application root
|   |-- manage.py
|   |-- passenger_wsgi.py
|   |-- requirements.txt
|   |-- LeaveManagementSystem/
|   |-- accounts/ ...
|   |-- static/
|   |-- staticfiles/           # generated by collectstatic
|   |-- media/                 # persistent uploads; preserve on updates
|   `-- tmp/
|-- app_public/                # subdomain document root only
`-- public_html/               # existing main site; do not change
```

Use these values:

| cPanel field | Value |
|---|---|
| Subdomain | `app.abirhkhandokar.com` |
| Subdomain document root | `/home/CPANEL_USERNAME/app_public` |
| Python Application Root | `leave_management` |
| Application URL | `app.abirhkhandokar.com` (root `/`) |
| Startup file | `passenger_wsgi.py` |
| Entry point | `application` |

The document root and application root should be different. This keeps source,
`.env`, database credentials, and Git metadata outside the web-accessible tree.
The cPanel Python application mapping connects the subdomain to Passenger.

In **cPanel > Domains**, create `app.abirhkhandokar.com` with document root
`/home/CPANEL_USERNAME/app_public`. If DNS is hosted on the same cPanel, the DNS
zone normally receives an A record automatically. Otherwise add an A record for
`app` pointing to the same server IP as the hosting account. Do not modify the
`www` record or `/home/CPANEL_USERNAME/public_html`.

After DNS resolves, run **SSL/TLS Status > Run AutoSSL** and confirm the
certificate explicitly lists `app.abirhkhandokar.com`. Test HTTPS before
enabling redirect/HSTS.

## 3. Create the Python application

1. Open **Software > Setup Python App > Create Application**.
2. Choose Python 3.12 or newer.
3. Set Application Root to `leave_management`.
4. Set Application URL to `app.abirhkhandokar.com` and `/`.
5. Set startup file to `passenger_wsgi.py` and entry point to `application`.
6. Create the app. Copy the activation command cPanel displays; its versioned
   virtualenv path is authoritative.

Typical SSH commands (adjust the version/path to the command displayed by
cPanel):

```bash
source /home/CPANEL_USERNAME/virtualenv/leave_management/3.12/bin/activate
cd /home/CPANEL_USERNAME/leave_management
python --version
pip --version
pip install -r requirements.txt
python -m django --version
```

If cPanel does not expose startup/entry fields, let it generate its default
`passenger_wsgi.py`, then replace that file with the repository version.

## 4. Environment variables

Add each variable in **Setup Python App > leave_management > Environment
Variables**. Do not upload `.env` to a public directory.

```text
DJANGO_SECRET_KEY=<new long random value; not the development key>
DJANGO_DEBUG=False
DJANGO_ALLOWED_HOSTS=app.abirhkhandokar.com
DJANGO_CSRF_TRUSTED_ORIGINS=https://app.abirhkhandokar.com
DB_ENGINE=mysql
DB_NAME=CPANEL_USERNAME_leave_management
DB_USER=CPANEL_USERNAME_leave_user
DB_PASSWORD=<strong unique password>
DB_HOST=localhost
DB_PORT=3306
SESSION_COOKIE_SECURE=True
CSRF_COOKIE_SECURE=True
SECURE_SSL_REDIRECT=True
TRUST_X_FORWARDED_PROTO=False
USE_X_FORWARDED_HOST=False
SECURE_HSTS_SECONDS=0
DJANGO_LOG_LEVEL=INFO
```

The main domain is intentionally absent from allowed hosts and CSRF origins.
Only add it if the Django app must genuinely receive requests on that hostname.

Start with `TRUST_X_FORWARDED_PROTO=False`. If HTTPS requests enter a redirect
loop and the host confirms Apache sends a trusted `X-Forwarded-Proto: https`
header, change it to `True`. Never trust this header without that confirmation.
After HTTPS is stable, HSTS can be enabled gradually (for example 3600, then a
longer value). Keep `SECURE_HSTS_INCLUDE_SUBDOMAINS=False` so this deployment
cannot impose HSTS policy on unrelated subdomains. Do not enable preload during
initial deployment.

## 5. MySQL/MariaDB and existing data

In **cPanel > MySQL Databases**:

1. Create database `leave_management`.
2. Create user `leave_user` with a strong generated password.
3. Add the user to the database with **ALL PRIVILEGES**.
4. Use the full cPanel-prefixed names shown by cPanel in the environment values.
5. Normally use host `localhost` and port `3306`; use different values only if
   the host documents them.

`PyMySQL` is included because it does not require compiling native client
libraries on shared hosting. The project package registers it for Django's
MySQL backend.

For existing SQLite data, first back up both `db.sqlite3` and `media/`. On the
local, unchanged SQLite configuration:

```bash
python manage.py dumpdata --natural-foreign --natural-primary \
  --exclude contenttypes --exclude auth.permission \
  --indent 2 > production-data.json
```

Upload `production-data.json` privately. Configure MySQL, run migrations, then:

```bash
python manage.py loaddata production-data.json
```

Test this on a staging database first. Keep the backup until record counts,
relationships, logins, and uploaded media have been verified. Delete the
private transfer file afterward.

SQLite can run a very small, low-write site, but its file must be outside the
document root and writable by the app. Its locking and backup limitations make
it a poor choice for this attendance/leave system with concurrent users.

## 6. Production commands

After dependencies and environment variables are configured:

```bash
cd /home/CPANEL_USERNAME/leave_management
python manage.py check
python manage.py check --deploy
python manage.py migrate --plan
python manage.py migrate
python manage.py collectstatic --noinput
python manage.py createsuperuser
```

Review the migration plan before applying it and take a database backup first.
Do not run `makemigrations` on the server: committed migration files are the
deployment artifact. `createsuperuser` is needed only if production has no
administrator yet.

## 7. Static and media files

WhiteNoise serves collected static assets from
`/home/CPANEL_USERNAME/leave_management/staticfiles` at `/static/`, including
admin CSS. Run `collectstatic` after every static-file change. Source assets in
`static/` are not the production output.

The defaults can be changed without editing code by setting
`DJANGO_STATIC_ROOT` or `DJANGO_MEDIA_ROOT` to absolute paths. This is only
needed if the host requires a different layout.

WhiteNoise intentionally does not serve user uploads. Keep persistent uploads
in `/home/CPANEL_USERNAME/leave_management/media`. If the host permits symbolic
links and Apache follows them, create:

```bash
ln -s /home/CPANEL_USERNAME/leave_management/media \
  /home/CPANEL_USERNAME/app_public/media
```

Otherwise ask the host to map URL `/media/` to that private media directory, or
use the host's supported public media directory and set `MEDIA_ROOT` through a
small hosting-specific settings override. Verify that direct `.env`, `.py`,
SQLite, and Git files are never exposed. Do not overwrite or delete `media/`
during releases; back it up independently.

## 8. Permissions and restart

Use directories `755` and files `644`. The Passenger account must be able to
write only where required: `media/`, `tmp/`, an SQLite file if retained, and an
optional private log directory. Use `750`/`640` for private configuration when
the host's Apache/Passenger ownership allows it. Never use `777`.

Restart using **Setup Python App > leave_management > Restart**. With SSH:

```bash
cd /home/CPANEL_USERNAME/leave_management
mkdir -p tmp
touch tmp/restart.txt
```

The `tmp/restart.txt` file belongs under the Python Application Root, not the
subdomain document root or main site's `public_html`.

## 9. Logs and troubleshooting

Check, in order: Setup Python App's application log, **cPanel > Metrics >
Errors**, the account/subdomain `error_log`, Passenger stderr, then any host
documented Apache log. Django logs to stderr by default so Passenger captures
startup and request failures. To add a rotating private file log, create a
writable `/home/CPANEL_USERNAME/logs` directory and set
`DJANGO_LOG_FILE=/home/CPANEL_USERNAME/logs/leave_management.log`.

| Error | Likely cause / check | Corrective action |
|---|---|---|
| 500 / Passenger startup failed | Missing package, bad env value, import path | Inspect Passenger/error log; activate venv; run `python passenger_wsgi.py` only as an import check or `python manage.py check`; reinstall requirements; restart |
| `ModuleNotFoundError` / no project module | Wrong Application Root or incomplete upload | Confirm `manage.py` and `LeaveManagementSystem/` are directly inside `leave_management`; use the provided startup file |
| `DisallowedHost` / 400 | Host missing from `DJANGO_ALLOWED_HOSTS` | Set exactly `app.abirhkhandokar.com`, restart |
| CSRF 403 | Wrong trusted origin, HTTP/HTTPS mismatch, stale cookies | Check `DJANGO_CSRF_TRUSTED_ORIGINS=https://app.abirhkhandokar.com`, certificate and proxy settings; restart and clear site cookies |
| Redirect loop | Django cannot detect proxy HTTPS | Confirm forwarded-header behavior with host before setting `TRUST_X_FORWARDED_PROTO=True` |
| Static/admin CSS missing | `collectstatic` not run or WhiteNoise absent | Install requirements, run `collectstatic --noinput`, restart, inspect browser `/static/...` request |
| Media 404 | No Apache link/alias or missing file | Check `MEDIA_ROOT`, symlink/host mapping, permissions, and exact filename case |
| Database connection failed | Prefix/host/password/privileges wrong | Compare cPanel's full DB/user names, grant privileges, run `python manage.py check`, inspect error log |
| `OperationalError` missing table | Migrations not applied to selected DB | Run `showmigrations`, `migrate --plan`, backup, then `migrate` |
| Permission denied | Wrong owner/mode on media/tmp/log/SQLite | Restore account ownership; use 755 dirs/644 files and only add owner write where needed |
| `ImportError` for MySQL | Requirements installed in wrong venv | Activate cPanel-displayed venv, install requirements, verify `python -c "import pymysql"`, restart |

The active models accept profile images only. Their form/model validation
limits files to JPG, PNG, or WebP and the profile forms cap uploads at 5 MB;
Django's `ImageField` uses Pillow to verify image content. An old `LAF`
migration mentions a generic attachment, but the current `LeaveRequest` model
has no attachment field. If arbitrary document upload is added later, validate
size, extension, MIME/content, authorization, and configure Apache never to
execute files under `/media/`.

source and generated files live outside `public_html`. Django accepts only the
subdomain hostname, so it will not capture or redirect main-domain traffic.
